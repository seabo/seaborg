## Implementation Notes

<!-- SECTION:NOTES:BEGIN -->
Implementation notes (crate is now `chess`, not `core`; task's core/src paths map to chess/src/ after the TASK-20 rename).

1. Bitboard::new: a From<u64> impl already exists for Bitboard, generated by impl_bit_ops!(Bitboard, u64) in bb.rs. So Bitboard::new(x) was redundant. Deleted it and migrated all 18 call sites (fen.rs x12, position/mod.rs x2, precalc/boards.rs x2, benches/bb.rs x2) to the Bitboard(x) tuple constructor, which is the dominant idiom across the crate (mod.rs already uses Bitboard(0) everywhere).

2. Board::new -> Board::empty; updated all 4 call sites (position/mod.rs, board.rs Default impl, board.rs x2 tests).

3. position::State renamed to CheckInfo. It holds checkers + per-player blockers + per-player pinners — i.e. check-and-pin information. Updated the definition, the pub use, the Position.state field type, mov.rs UndoableMove.state field, fen.rs, and all doc comments. Kept the field name `state` and module file state.rs (the struct name was the scoped item; the field is a reasonable generic name for the position's cached derived data). The rename is confined to the chess crate — no other crate references chess::position::State.

4. Deleted the three stale TODOs in position/mod.rs (pub-fields getters, Arc-wrapping, better-name) and the impl_bit_ops TODO in macros.rs.
   - Arc decision (recorded on the Position.state field): CheckInfo is held inline, not behind an Arc. Pleco wraps its state in an Arc to make Position cloning cheap, but Position is cloned rarely here and CheckInfo is a handful of bitboards, so Arc would only add reference-counting to the hot make/unmake path to save a copy that barely costs anything.
   - impl_bit_ops decision (recorded on the macro): the macro already provides Bitboard's raw operators (impl_bit_ops!(Bitboard, u64) in bb.rs). The TODO wanted to route *everything* through it. Bitboard's semantic methods (bsf, pop_lsb_and_bit, its Iterator impl) stay hand-written on purpose because they return domain types like Square rather than raw u64; generalising them through a bit-ops macro would strip those types back to integers and undo the domain-safety boundary TASK-48 established.

5. Piece::player: benchmark decision. Compared the 13-arm match against an arithmetic form (Player((piece as u8) > 6), keeping the panic-on-None arm) using cargo bench --bench perft (perft's make_move exercises player() on the hot path). Match baseline: perft 5 = 22.8/23.1/23.6 ms. Arithmetic variant vs that baseline: change [-0.23% +1.90% +3.76%], 'Change within noise threshold' with the point estimate slightly slower. No real gain, so the match stays and the TODO is removed. The match compiles to a jump table as the task anticipated.

6. Verification and no-regression: fmt/clippy/test below. perft 5 held at ~23 ms (unchanged from the match code path). The only test failure is engine::search::tests::an_extendable_budget_is_still_bounded_by_its_hard_half, a wall-clock timing assertion that flakes under the full engine-lib parallel load (perft suites saturating all cores deschedule the search thread past its 160ms tolerance). It passes 10/10 in isolation on this branch, and reproduces at the base commit c831d5a under equal interleaved load (base failed 1/3, branch 1/3 in a back-to-back A/B). My diff touches zero engine/ files and only makes chess equal-or-faster in debug, so it cannot be the cause.
